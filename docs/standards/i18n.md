# i18n Standards

The app ships in English and Czech via react-i18next. Locale files live in
`src/i18n/locales/en/<namespace>.json` and `src/i18n/locales/cs/<namespace>.json`,
one namespace per domain.

## 1. Every string lands in BOTH locales

Every user-facing string goes into **both** `src/i18n/locales/en/<ns>.json` **and**
`src/i18n/locales/cs/<ns>.json` in the same change.
**Why:** `fallbackLng: 'en'` (`src/i18n/index.ts`) masks missing Czech keys — an
en-only string renders fine in both languages, passes every gate silently, and rots
the cs locale one key at a time. No tool catches this; only the both-files rule does.

## 2. New namespaces are registered

A new namespace JSON file does nothing by itself: import both locale files and register
the namespace in `src/i18n/index.ts` (the `NAMESPACES` list and the `resources` map).
**Why:** an unregistered namespace makes `t()` return raw keys at runtime with no
build-time error.

## 3. Component usage pattern

```tsx
const { t } = useTranslation('<domain>');       // domain strings
const { t: tc } = useTranslation('common');     // shared strings (buttons, labels)
```

Domain strings live in the domain namespace; generic strings (Save, Cancel, Delete…)
come from `common` — don't duplicate them per domain.

## 4. Backend errors are i18n keys

Backend `AppError::Validation` carries i18n keys (e.g. `"validation.bondNameRequired"`),
not English text. The frontend maps them with `translateApiError`
(`src/lib/translate-api-error.ts`) before display — see
`docs/standards/rust-backend.md` rule 3 and `docs/standards/typescript-frontend.md`
rule 6. Adding a new backend validation key means adding its translation to both
locales, same as any other string.

## 5. Verification

After touching a namespace, verify both files parse and their keys match:

```bash
node -e "JSON.parse(require('fs').readFileSync('src/i18n/locales/en/<ns>.json'))"
node -e "JSON.parse(require('fs').readFileSync('src/i18n/locales/cs/<ns>.json'))"
```

Then eyeball key parity for the namespace you touched (same keys on both sides — a
diff of sorted key lists works). There is no automated parity gate yet; the check is
on you.
