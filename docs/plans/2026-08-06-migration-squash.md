# Migration squash to single baseline (2026-08-06)

> Frozen snapshot — describes the one-time squash performed before open-sourcing. Not current truth.

## Why

37 append-only migrations (001–037) accumulated during solo development. Telemetry (Aptabase) confirms zero external users; the only production database is the author's own. Squashing to a single baseline makes the schema readable for contributors before the repo goes public. Rule 6 of CLAUDE.md (append-only migrations) is intentionally waived once for this operation and applies again from the new baseline onward.

## Design

1. **Golden fixture**: dump the exact schema (`sqlite_master`) and seeded data (`transaction_categories`, `institutions`) produced by the old 37-migration chain into `src-tauri/src/db/golden_schema.snapshot`. Generated by an `#[ignore]`d test while the old chain still existed.
2. **New baseline**: `MIGRATION_001` ("001_baseline") is generated from the golden fixture — final `CREATE TABLE`/`CREATE INDEX` statements (with `IF NOT EXISTS` injected) plus `INSERT OR IGNORE` seed rows. Identity with the old chain is therefore by construction, and enforced forever by a test comparing baseline output to the fixture.
3. **Legacy upgrade path** (the author's own DB): the runner inspects `_migrations`:
   - contains `037_multicurrency` → fully migrated legacy DB → stamp `001_baseline` without executing anything; data untouched.
   - contains older names but not `037_multicurrency` → hard error: "open this database with Moony v1.3.0 first to finish legacy migrations".
   - empty → fresh DB → execute the baseline.
4. **Tests**: (a) baseline output == golden fixture (schema + seed rows); (b) simulated legacy DB (built from fixture + fake `_migrations` rows) passes through the runner unchanged and gets stamped; (c) partially-migrated legacy DB errors.

## Out of scope

Calculation-logic audit (separate task), demo seeder, any schema *changes* — the baseline reproduces today's schema exactly, flaws included.
